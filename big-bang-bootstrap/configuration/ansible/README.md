# Platform bootstrap and configuration operations

These are explicit Ansible operations, not another reconciler. All apply/verify gates default false; check mode must not contact APIs or read private inputs. configuration/ holds desired package/identity YAML; this directory executes reviewed bootstrap/application API steps.

## Readiness and activation order

Dependency chain: RKE2 → Flux foundation → Big Bang umbrella → Longhorn → storage acceptance → Rancher. Flux reconciles both the umbrella and the child HelmRelease generated by Big Bang. Longhorn is the first platform package, after the GitOps foundation.

1. Infrastructure: verify RKE2 nodes Ready and the reviewed worker-only Longhorn prerequisites, labels, capacity and enforcing SELinux. Host preparation is already complete; do not rerun installation on existing hosts.
2. Release and Flux: publish the reviewed core-only source and verify its immutable release/context. Install the pinned Flux foundation and seed a paused source/root using the exact kubeconfig/context/UID. Platform v0.9.0 selects identity applications and is not the Longhorn-first input.
3. Longhorn prerequisites: after Flux namespaces exist, explicitly approve longhorn-prerequisites.yaml to apply common Big Bang and Longhorn namespace/installer RBAC. Review privileged permissions. No application TLS, identity namespace or tenant authority is needed for this stage.
4. Longhorn activation: select a new published release containing the active outer release and Longhorn child. The v0.10.0 staging release keeps them suspended and cannot activate storage. Separately approve resuming the release-pinned seed source/root after the prerequisites above. The first storage-only release v0.11.3 passed this checkpoint. This candidate also selects Rancher and OpenBao, so do not mistake it for the initial storage-only input. Shared Headlamp defaults remain disabled and identity values references optional. Run readiness.yaml phase storage. Validate a disposable claim with write/recreate persistence, reattachment and two healthy replicas on distinct workers before proceeding. Readiness alone does not prove durable I/O or backup recovery.
5. Rancher: storage acceptance passed and this candidate selects its package in the same authoritative root. Approve its namespace/installer RBAC, Rancher-only TLS/public CA delivery and external bootstrap-values Secret separately, then its Helm activation. Rancher has no fabricated PVC dependency; this ordering is an operator acceptance checkpoint. Verify HTTPS and local administration before adding SSO.
6. Initial app access: the default `clusters/local` root selects OpenBao only, retaining Longhorn/Rancher. After OpenBao acceptance, `clusters/local-headlamp` adds token-mode Headlamp; after Headlamp acceptance, `clusters/local-keycloak` adds Keycloak and its database. Use the [ordered app stages](#ordered-app-stages) within the same immutable release. Source selection is not live deployment approval. Deliver reviewed prerequisites and named credentials/TLS, then validate placement/storage and the per-app health report below. OpenBao initialization/unseal and Headlamp token identity require their own approved scope; token-mode Headlamp does not depend on Keycloak. For later OIDC, PostgreSQL/Keycloak readiness precedes realm/client, API OIDC and app SSO configuration; those security changes remain separate. API OIDC maintenance includes protected configuration backup and a separately approved control-plane restart.
7. Enrollment remains omitted. Only after core and identity/security acceptance, select ../../enrollments/local and review compatible published downstream inputs and source/reconciler activation. Its retained definitions stay independently paused. readiness.yaml phase enrollment observes the parent; tenant foundations/apps remain in enrollment/application Git.

Kustomize file order is not readiness. Database startup also retains a bounded native readiness init-container. Checks observe status; they never activate, scale or create extra reconcilers. Enabling gates or resuming resources outside reviewed source cannot replace this sequence.

## Health and capacity acceptance after every app

After each successful app deployment, provide the operator a timestamped health/
resource breakdown before calling that stage accepted or starting the next app.
Reuse the existing read-only resource snapshot command set and the explicit
kubeconfig/context/cluster-UID gate in [readiness.yaml](readiness.yaml): Kubernetes
node/pod status, metrics API (`kubectl top nodes` and `kubectl top pods -A`), node allocation/request/
limit summaries and Longhorn node/volume/replica status. Do not install metrics
components, read Secret data, repair or change workloads as part of this report.

- Per node: actual CPU and RAM usage with units/percent of allocatable, separately
  from summed pod requests/limits; identify unrequested/unlimited workloads and
  overcommit. Missing/stale metrics mean unavailable, never zero or requests-as-use.
- Node Ready/pressure, pod/controller readiness, Pending/failed/crash-looping pods,
  restarts and the largest consumers; distinguish expected completed jobs and
  intentionally detached volumes from failures.
- Per Longhorn worker: raw/free/reserved/scheduled disk space, healthy versus
  degraded replica/volume state, two-copy overhead and remaining usable headroom.
  Replication is not backup; do not equate scheduled capacity with measured bytes.
- Where comparable, show the delta from the previous app's snapshot, naming both
  timestamps/versions and sample age. An instantaneous quiet sample is not a peak
  load or full-stack capacity guarantee. Explain any noncomparable baseline.

Save safe results/status automatically with that app's protected `.rke2-state/`
run evidence; public handoff contains only sanitized aggregates/limits and evidence
references. Do not require the operator to transcribe terminal output. This is an
acceptance requirement within each approved deployment/acceptance batch, not
authority to deploy apps, change access or repair health, and not a claim that a
new reporting wrapper exists. A failed readiness/health gate stops the next stage;
no automatic eviction, cleanup or capacity repair.

After the app stages, an early Grafana goal is a cluster overview covering these
same node/workload/storage signals. Assess the six queued starting dashboards in
[metrics draft #111](https://github.com/perkforge/perkforge-platform/pull/111) first.
A community dashboard is welcome after reviewing its metric names, RKE2/exporter
labels, datasource UID/variables, units, plugin/version/license requirements and
access boundaries. Keep reviewed dashboard JSON/datasources in Git; no blind
imports or unsupported metrics presented as healthy zeroes. Grafana deployment
and dashboard/live-data acceptance remain separate future approved work.

The separate `clusters/local-nextcloud` stage preserves `local-gitlab-runner`
packages and selects only the released Nextcloud enrollment path. Do not select
the Portal enrollment root for this app. Its generic prerequisites use the explicit
`gitops_path`, require a direct enrollment selection and validate the rendered scoped
parent before release/cluster checks or authority changes. The default local root
still excludes enrollment and is refused. Publish/verify the enrollment pin before
publishing this stage; no UNCONFIGURED value is a deployment input.

After approved prerequisites and protected inputs, promote the published platform
tag and this path through the existing conditional source/root procedure. Never
rerun bootstrap. Accept CNPG readiness, actual dedicated SSD replica IDs and verified
database TLS before a later released web stage. Initial claim sizes remain 16Gi
database and 32Gi files; no household import or old-volume migration is included.

DNS preparation makes no network changes: verify `nextcloud.perkforge.home.arpa`
resolves to approved Ready Traefik node ingress addresses, not a ClusterIP/Pod IP.
The old VM hostname/hosts entry is unrelated. For initial routing/TLS verification
when LAN DNS is pending, an owner can use explicit approved nonsecret inputs:

```sh
curl --fail --show-error --connect-timeout 10 --max-time 30 \
  --cacert "${NEXTCLOUD_INGRESS_CA:?public ingress CA path}" \
  --resolve "nextcloud.perkforge.home.arpa:443:${NEXTCLOUD_INGRESS_IP:?approved LAN ingress address}" \
  https://nextcloud.perkforge.home.arpa/status.php
```

This keeps hostname/certificate verification enabled and writes no DNS/hosts file.
It is a diagnostic, not household DNS setup or app/backup acceptance. Signing keys,
leaf private keys and passwords stay outside source and chat; the approved enrollment
input playbook delivers only new app credentials and the ingress leaf key. No existing
credential discovery is implied by this procedure.

## Longhorn-only release and seed activation

The first storage-only stage is complete on the physical cluster at v0.11.3.
This candidate includes Rancher and OpenBao; it is not the first storage-only release. The live
source/root are active, so **do not rerun bootstrap or pause them for routine
promotion**. Rancher activation is also complete at the last verified v0.12.0
checkpoint; use [ordered app stages](#ordered-app-stages) for the next separately
approved activation. The [Rancher procedure](#rancher-local-admin-stage) remains
the reference for that earlier rollout.

For a new cluster, choose a reviewed storage-only published release for the first
stage, not this multi-app candidate. Its initial sequence remains:

1. Verify immutable tag/commit and clean checkout; keep `config_tag`, release
   evidence, kubeconfig/context/UID in protected external runtime inputs. No main,
   feature branch or self-referential future tag is a deployment input.
2. Separately approve initial `bootstrap.yaml` (`bootstrap_apply=true`) to install
   pinned Flux and create a **paused** source/root. Registry delivery is independent
   and never overwrites. Bootstrap intentionally pauses the seed and is not a
   maintenance reconciler for an already active cluster.
3. Apply reviewed common/Longhorn prerequisites with explicit approval and verify
   host compatibility, worker selection/capacity and privileged installer scope.
4. Approve the exact source/root URL/tag/path/context/identity; resume the source,
   verify its exact fresh artifact, then resume the root. The seed is not included
   in its own Git tree, and child suspension comes only from reviewed Git values.
5. Check storage readiness, then separately approve the disposable persistence/
   reattachment/two-replica test. Retain its data until cleanup approval. Readiness
   and replication do not prove backup/restore or HA. Only then review Rancher.

For the current active cluster, promotion is a conditional tag change after
prerequisites/inputs are ready, followed by exact artifact/root/child verification.
Do not manually resume an individual child against contradictory Git values or
reset failed releases automatically. A new failure needs diagnosis and approval.

Flux documents [artifact revisions](https://fluxcd.io/flux/components/source/gitrepositories/)
and [Kustomization suspension](https://fluxcd.io/flux/components/kustomize/kustomizations/).
No source merge/release or runtime input is live execution approval. Preserve
recovery inputs and logs; suspension does not remove workloads or retained data.

## Repeatable Flux registry preparation

The pinned Big Bang Flux foundation uses Iron Bank controller images. All four
controller Deployments already reference `flux-system/private-registry`; no node
registry configuration, image replacement, service-account patch or restart
annotation is required. OS registration and Git source authentication do not
supply registry authentication.

Use a clean checkout of a published release containing this registry step, with
its matching `config_tag` and release evidence. Bootstrap verifies both the
executing commit and clean tree before API work. Supply the normal explicit
kubeconfig/context/cluster UID and pinned upstream checkout destination in a
protected external YAML file; never put local deployment inputs or credentials
into tracked values. The additional input contract is:

| Input | First creation | Reuse |
|---|---|---|
| `bootstrap_apply` | Explicitly approved `true` | Explicitly approved `true` |
| `bootstrap_registry_apply` | Separately approved `true` | `false` (default) |
| `registry_username` | Registry1 username | Not read |
| `registry_credential_file` | Absolute path to nonempty owner-only `0600` regular token/password file; no symlinks | Not read |

From the selected clean release root, set `PLATFORM_INPUTS` to the absolute path
of that protected input file, then run after approval:

```sh
ansible-playbook -i big-bang-bootstrap/configuration/ansible/inventory.yaml \
  big-bang-bootstrap/configuration/ansible/bootstrap.yaml \
  -e "@$PLATFORM_INPUTS" -e bootstrap_apply=true -e bootstrap_registry_apply=true
```

The normal bootstrap gate encloses all registry operations. Default and check
mode do not contact Kubernetes or read credentials. Release/context/cluster and
upstream commit checks precede mutation. Bootstrap extracts/applies only the
Namespace from the pinned upstream render, then creates the missing named Secret
through redacted stdin before applying controllers. No credential manifest is
written to disk, logged or passed in process arguments. Existing credentials are
never overwritten: with the delivery flag false, bootstrap checks the named
Secret's Docker-config type and Registry1 auth structure under redaction, without
opening the local credential file. Structure checks do not prove credentials are
valid; controller readiness verifies actual image pulls. Rotation is separate.

For a retry or a cluster with an existing compatible Secret, use the same command
with `bootstrap_registry_apply=false` and omit local registry inputs. Bootstrap
still reapplies a **paused** source/root; do not rerun it as routine maintenance
after activation. A failed controller wait leaves the seed unapplied. Inspect
Flux events and credential scope before retrying; do not delete the namespace or
change pinned images. The first physical attempt recovered by creating the
already-referenced Secret and recreating only failed controller pods. Those
manual recovery actions are not part of the repeat procedure.

Published v0.11.1 and later contain this registry step. Preserve the original
v0.11.0 release unchanged. The current v0.11.3 cluster is active and reuses its
existing Secret; registry repair/rotation is not part of ordinary source promotion.

## Containment and recovery

Pause the affected root first, then the affected child source/reconciler/release before manually stopping new workloads. Root suspension stops manifest updates, not running services or every child controller. Preserve retained database data, backups and existing healthy Flux/services. Resume only from a reviewed canonical configuration; do not let an active parent undo containment. Existing published tags/old paths remain unchanged and provide historical source, not permission to run removed workflows.

Keep private logs locally with timestamps, symptoms, confirmed causes versus hypotheses, fixes and verification; no token/password/Secret bodies or shell tracing around credentials. The temporary laptop guardian was operational trial tooling, not a controller deployed by this code. Physical observation thresholds/duration and recovery actions require a new measured plan.

Rancher OIDC/admin configuration lives in `configure-rancher-oidc.yaml`, with
explicit private inputs overriding `vars/rancher-oidc.yml`. It is default-off,
contacts no cluster in check mode, and requires separate security-change approval
after Rancher and Keycloak readiness. See the Rancher package README. Infrastructure
contains no direct Rancher installer or Rancher API operations.

## TLS prerequisites before application activation

Client HTTPS terminates at Traefik. The authored Headlamp/Keycloak Ingress routes
forward HTTP to their backend Services; a TLS Secret supplies Traefik's hostname
certificate/key rather than requiring an HTTPS listener in every application pod.
Each Ingress references a Secret in its own namespace, so the current design uses
separate application TLS Secrets. Shared/default ingress certificates would be a
separate architecture choice, not something these delivery tasks configure.

Public CA resources have a different purpose: clients making outbound HTTPS calls
must trust the presented chain. Headlamp needs the CA for Keycloak discovery/token
validation; Rancher uses public CA resources for its private-CA/strict-agent and
outbound trust contracts. OS trust does not populate container trust automatically.
Ingress termination does not provide encryption on backend/internal connections;
OpenBao listener/Raft TLS and any future backend HTTPS remain separate decisions.


`platform-tls.yaml` prepares only explicitly named Headlamp/Keycloak/Rancher inputs.
Both platform_tls_namespaces_apply and platform_tls_apply default false; check
mode never reads key files or contacts Kubernetes. The first flag creates only
missing authored Namespace objects. It does not select charts, grant installer
RBAC, create PVCs or apply routes. Headlamp/Keycloak retain their standard namespace
labels; cattle-system retains the explicitly privileged PSA label required by its
separate reviewed package namespace. Rancher's Namespace file is split from
installer.yaml so namespace preparation cannot accidentally grant cluster-admin.

The delivery flag validates all selected leaf/key pairs and the recorded CA
fingerprint before writes, then creates (never overwrites) these exact resources:

| Namespace | Resource | Material |
|---|---|---|
| headlamp | Secret/headlamp-local-tls | Headlamp leaf and service key |
| headlamp | ConfigMap/identity-ca, ca.crt | Public root only; existing OIDC mount |
| keycloak | Secret/keycloak-local-tls | Keycloak leaf and service key |
| cattle-system | Secret/tls-rancher-ingress | Rancher leaf and service key |
| cattle-system | Secret/tls-ca, cacerts.pem | Public root for strict agent trust |
| cattle-system | Secret/tls-ca-additional, ca-additional.pem | Public root for outbound Keycloak trust |

Select an explicit nonempty platform_tls_applications list from headlamp, keycloak
and rancher; default is empty. OpenBao is rejected until its listener/localhost/
internal TLS contract is resolved. No root signing key is read or delivered.
Use the normal local platform inventory plus protected external vars for reviewed
config_tag/config_release_evidence, target_kubeconfig/target_context,
expected_cluster_uid, platform_tls_bundle and platform_tls_expected_ca_fingerprint.
All normal release checks apply: published immutable source, matching selection
annotations, exact clean checkout and exact cluster. Uncommitted work cannot be applied through this gate. Review/publish a compatible release first.

After release review and action-specific approval, invoke platform-tls.yaml with
platform_tls_applications set explicitly and the separately approved namespace/
delivery flags. Public CA identity and certificate chain/hostname/server purpose,
minimum30-day lifetime, matching keys, private directory/key modes and symlinks are
checked. Existing namespaces must match authored ownership/PSA labels. Existing
TLS/CA objects cause refusal, not implicit adoption/rotation. Creates use JSON over
stdin under no_log; no rendered credential manifest is written to disk or Git.
TLS readback verifies the exact stored certificate/key under redaction. Credentials
in transient facts are cleared. Partial failures can leave earlier objects created;
inspect metadata and plan resume/rotation explicitly rather than deleting them or
bypassing guards. There is no automatic credential rollback or prune.

This prepares inputs only. Routes, Headlamp/Keycloak deployment, Rancher selection,
API-server CA path/OIDC activation and live HTTPS still need separate operations.
Do not enable the legacy Keycloak local-PV path just to create its namespace: this
namespace-only stage has no storage dependency and does not bypass Longhorn checks.

## Ordered app stages

One immutable published artifact contains these standard Kustomize roots:

| Order | Root `spec.path` | Selected apps |
|---|---|---|
| 1 | `./big-bang-bootstrap/clusters/local` | Existing Longhorn/Rancher plus OpenBao |
| 2 | `./big-bang-bootstrap/clusters/local-headlamp` | Stage 1 plus token-mode Headlamp |
| 3 | `./big-bang-bootstrap/clusters/local-keycloak` | Stage 2 plus Keycloak and PostgreSQL |
| 4 (optional, separate approval) | `./big-bang-bootstrap/clusters/local-headlamp-sso` | Stage 3 packages with externally delivered Headlamp OIDC credentials/public trust; API OIDC/restart prerequisites required |

The required final `values-app-stage` ConfigMap overrides earlier package selection.
Stages 1–3 change package selection without OIDC integration. Stage 4 selects
Headlamp OIDC workload configuration; it does not create credentials, grants or
installer rights. Roots already present in one verified release share its tag/commit.
A newly authored root requires a new release containing it before selection.
These are stage paths for the same physical target, not new clusters.

Headlamp SSO selection requires a verified immutable release that contains stage 4,
not merely the app adapters. Existing token-mode stages and the active source stay
unchanged until explicit promotion approval. Follow the [Headlamp release and
activation gate](../authorization/sso/README.md#headlamp-source-selection-and-release-gate)
for credential delivery, sole-control-plane maintenance, acceptance and rollback.

1. Review the exact release render at stage 1, existing target/UID and prerequisites.
   Deliver only separately approved TLS/bootstrap inputs and installer prerequisites.
   Prerequisite playbooks retain the base local path as their verification input;
   do not rerun Flux bootstrap or pause existing reconcilers.
2. Separately approve OpenBao activation and initialization/unseal custody. Promote
   the active source only with current-tag/resourceVersion guards; verify the exact
   fresh artifact. Keep root at the default path. Stop on drift/failure/timeout.
3. Complete OpenBao readiness, admin-access/custody acceptance and the required
   health/capacity report. Uninitialized/sealed state is not successful acceptance.
4. After Headlamp inputs/prerequisites and explicit approval, conditionally change
   only the existing root path from stage 1 to stage 2. Check the expected old path,
   resourceVersion, active source and exact artifact first. Preserve saved results;
   verify Ready, approved token access and health/capacity before continuing.
5. After Keycloak/database credentials, TLS, prerequisites and explicit approval,
   similarly advance stage 2 to stage 3. Verify database/Keycloak readiness, initial
   master-admin access and health/capacity. Realm/group/app authentication remains
   a separate disabled proposal requiring approval.

No live promotion command is authorized by this procedure. There is no new stage
controller: the operator uses the existing guarded Kubernetes access, saving each
conditional patch and observed result automatically. Never substitute arbitrary
paths or move backward as automatic rollback: disabling a package can uninstall it.
On a failed stage retain its path, objects, data and diagnostics; decide recovery
explicitly. Do not prune a previous app to make capacity appear adequate.

## Logging pilot protected inputs

`logging-inputs.yaml` defaults off and reads no private files or Kubernetes API in
that state or in check mode. It is limited to the released `local-logging-pilot`, `local-logging-backend` or `local-logging-limited-pilot`
source, the pinned physical cluster UID, and prepared monitoring/logging/alloy
namespaces. This is input delivery, not workload activation or acceptance.

Supply owner-only (0700) `logging_private_dir` containing 0600 `username`,
`password`, and `htpasswd` files. The machine username uses lowercase letters,
digits, underscores or hyphens, starting with a letter or digit (at most 32
characters). The password is 64–256 alphanumeric characters. `htpasswd` contains
exactly that username and its SHA512-crypt entry. Both collection and query use
this same pilot identity because the gateway derives the Loki tenant from it.
The credential permits reads and writes; this pilot remains platform-admin-only.
It does not establish tenant-safe Grafana authorization.

Supply a 0700 `logging_tls_dir` with 0700 `gateway` and `backend` directories,
each containing 0600 `tls.crt` and `tls.key`. The certificates must have exactly
the corresponding service DNS identity (`logging-loki-gateway.logging.svc.cluster.local`
and `logging-loki.logging.svc.cluster.local`), match their keys, chain to the
0600 public `logging_ca_file` (exactly one pinned certificate, with no host-default
trust fallback), permit server authentication, and remain valid
for more than 30 days. Pin the public certificate's DER SHA256 fingerprint in
`logging_expected_ca_sha256`. No CA signing key is read or delivered.

After review of the exact released source and separately authorized delivery,
set `logging_inputs_apply=true` with those paths and the existing target/release
inventory. The playbook server-validates every missing object before creating
any. Its nine fixed targets are TLS/auth/pull Secrets in logging and alloy,
monitoring/loki-query-auth, and public loki-ca ConfigMaps in monitoring and alloy.
Registry credentials are copied only from the existing Registry1-only Flux
Secret. All targets are immutable and owned; identical repeats make no changes,
and unowned or changed objects fail instead of being adopted or rotated. Private
values pass through redacted stdin. Nothing here authorizes collection beyond
the opt-in logging-pilot namespace or changes the active Flux root.

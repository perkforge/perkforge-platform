Human-operated physical provisioning

Context → workstation/node/platform → focused operating views. Use topology for the actual workstation/three-node network. Full commands belong in the single operator runbook; these notes explain architecture and completion boundaries.

  1. Prepare reviewed PXE configuration — Review target, network, media and fresh private configuration.
  2. Review target, disk and action scope — Confirm selected node, disk, data loss and access scope.
  3. Activate PXE and select network boot — Start reviewed services and reach the indefinite GRUB menu.
  4. Install RHEL with reviewed settings — Review layout and accounts before committing the installation.
  5. Restore disk-first and boot installed OS — Restore firmware order and verify the installed disk boots.
  6. Verify identity, key login and sudo — Establish trusted access and verify fresh login and sudo.
  7. Stop owned services and retain evidence — Verify scoped shutdown and preserve original services and evidence.

Operator responsibilities

The human selects/approves the node, disk and access scope, operates firmware/Anaconda and verifies physical host identity. Tools run only on deliberate invocation. Viewing C4 performs no provisioning. Secrets and host public-key pins are excluded; Physical IP/MAC values remain in an ignored local inventory.

1. Prepare reviewed PXE configuration

Use the single human-run installation runbook. Verify the DVD/boot tree and existing service identities. The operator supplies confirmed metadata to the shared offline Ansible renderer; generated work is not approval to start services. See working-directory construction.

Operator
Select the target and review actual metadata/media.
Automation
Explicitly invoked Ansible validates and renders inert private files only.
Evidence / stop
Fresh output and reviewed hashes; stop on missing identity or unexpected state.

2. Review target, disk and action scope

Review this physical node and action scope. Inspect its internal-drive count, model, capacity and device before approving all existing-data loss. Approve account/access privileges separately; prior-node approval never transfers.

Operator
Approve exact target, exposure, erase and access scope.
Automation
Serving checks do not attest physical disk identity.
Evidence / stop
Sufficient disk evidence and current action approval; no inferred erasure.

3. Activate PXE and select network boot

The existing router allocates DHCP addresses; proxy dnsmasq supplies boot metadata, TFTP serves the vendor EFI chain/menu/kernel/initrd and HTTP serves the complete DVD tree. Keep Secure Boot enabled. Use one-time wired UEFI IPv4 PXE, or record a temporary network-first Primary Boot Sequence change. The menu waits indefinitely and defaults to exit; select the interactive installer deliberately. PXE supplies no remote disk-inventory agent.

Operator
Run approved serving and select the reviewed physical boot path.
Automation
Dedicated guarded services respond to client requests.
Evidence / stop
Reviewed GRUB menu and expected installer; stop on trust, target or network error.

4. Install RHEL with reviewed settings

In Anaconda, choose the approved disk and Custom layout: 600MiB EFI, 2GiB standard XFS /boot, remaining XFS root on ordinary LVM. This local-lab profile has no separate home/swap, encryption or FIPS. Review selected-disk-only changes, Minimal Install, node hostname/wired network/timezone, disabled root and named administrator/password. Begin Installation commits storage. Keep the source available through explicit completion.

Operator
Configure and approve the interactive layout/accounts before committing.
Automation
Standard Anaconda installs packages from HTTP; no unattended installer is included.
Evidence / stop
Explicit installation success; progress/task count is not completion.

5. Restore disk-first and boot installed OS

After completion restore disk-first in the relevant Primary Boot Sequence and Automatic Boot Sequence. Keep Secure Boot and verify a full boot with Ethernet connected. If PXE/no-OS loops occur, inspect both sequences, drive detection and the RHEL UEFI entry before repair. Disconnecting Ethernet can help reach disk boot but is not proof saved ordering is correct.

Operator
Restore firmware order, then confirm installed login/hostname.
Automation
Firmware boots the installed disk; no unattended reboot controller.
Evidence / stop
Connected disk boot without installer loop; preserve console access on failure.

6. Verify identity, key login and sudo

Compare complete host identity through physical console before trusting SSH. Use the existing public key and the shared access handoff; prove fresh key-only login and password-authenticated sudo. Review resulting storage/network/time. OS/access does not authorize RKE2.

Operator
Verify physical identity and enter credentials locally.
Automation
Standard SSH and the checked helper perform only the approved access work.
Evidence / stop
Fresh key-only login/password-sudo; stop on mismatch and retain recovery access.

7. Stop owned services and retain evidence

After source is no longer needed, invoke the separately approved identity-checked stop. Verify owned units/processes/listeners and matching guard gone, with original services preserved. Keep only needed current configuration/trust; discard disposable runs deliberately after review. Repository cleanup never changes native resources or node credentials.

Operator
Approve shutdown and review its result.
Automation
Ansible stops only exact recorded resources.
Evidence / stop
Scoped absence verified; mismatch means incomplete, not broad-reset permission.

Operator working-directory construction

A human fills nonsecret inputs and deliberately runs workspace.yml. It invokes shared prepare.yml, creates a fresh run with mode0700 directories/mode0600 files, retains exact configuration copies/hashes and emits a standard session.sh caller. It performs no live action. Existing paths/symlinked ancestors and UNCONFIGURED required inputs are refused. A source copy is not human approval.

pxe/local/<node>/runs/<fresh-run>/
  inputs.yml, README.md, session.sh
  discovery/  #rendered files, activation-review.yml, later output summaries
  access/     #later real trust-run evidence; starts empty

Each access run uses handoff-<unique>/ with a candidate key, real physical-match confirmation and known_hosts. summary.txt records bounded results, never password input. Current inputs/inventory and existing trust are not served or watched. The checked source and a human input file reproduce generated work without AI; actual keys/passwords/trust/events cannot be fabricated. Retain required current recovery material before discarding disposable runs. See the runbook for exact commands and prior-session preservation.

Serving lifecycle and ownership

Fresh activation refuses existing native roots/units/table/ports. Ansible places unique root-controlled configuration, verifies hashes and read-only media, creates an exclusive dedicated ingress table before LAN binding and launches only dedicated units. Default1800seconds is bounded; explicitly selected0 maps to RuntimeMaxSec=infinity with manual-stop responsibility. Original router/system/libvirt services are not reconfigured.

Shutdown checks recorded config/unit invocation/guard identity before scoped stop/removal. Prior stopped roots may be preserved only by a separately reviewed exact-state operation with fresh destinations. No broad resets, service kills or firewall flushes. Private logs honor no_log and never record terminal/password input.

Installed-host trust and access

Compare the complete host fingerprint through physical console, then pin it; a scan alone is not trusted identity. The shared access.sh invokes standard SSH and the unchanged checked policy helper. It requires an existing key reference and protected confirmed trust files, verifies expected host/user/client, hashes the transferred helper, checks effective policy before reload and tests a separate fresh key-only/password-sudo connection. It refuses a preexisting managed drop-in. No private key is transferred, no credential is generated and passwords stay local. Retain console/current access until success.

Platform boundary

Host repositories, kernel modules, time, swap, storage/capacity, SELinux, CNI/NetworkManager, firewall/forwarding and credential/snapshot custody require review before RKE2. Infrastructure Ansible owns host/RKE2 and gated Rancher API configuration; optional Longhorn/Rancher Helm deployments belong to Big Bang/Flux. Rancher is platform-admin cluster lifecycle; Flux owns GitOps; Big Bang supplies curated packages. Tenant enrollment and application repositories retain their respective ownership. No OS/access or repository-cleanup approval enables these later changes.

RKE2 architecture and repeat process

One control-plane/embedded-etcd server and two agents form a single-server cluster, without control-plane high availability. Canal provides pod networking; Traefik provides ingress. RHEL repositories, enforcing SELinux, kernel modules, forwarding and NetworkManager CNI exclusions precede the pinned RPM installation. Canal host preparation explicitly stops/disables firewalld under separate approval.

Repeat order: register RHEL and enable BaseOS/AppStream; review and run host preparation; create a protected separate agent-only token; install the server; join workers serially; verify exact node names Ready and system pod readiness. Infrastructure Ansible owns these steps. Host preparation refuses an existing RKE2 installation. Defaults/check mode make no remote connection; live actions require explicit approval.

The server token permits privileged joins and encrypts bootstrap recovery data. The two workers share a separate agent token. Keep both complete tokens and the administrator kubeconfig in protected independent custody, outside Git and served assets. Recovery requires the server token with matching etcd snapshots. Local credential exports and Ready nodes do not prove backup/restore readiness. Actual addresses and private state stay in ignored inventory files.

The explicitly invoked workload smoke test renders a disposable two-pod/service fixture on two distinct workers. It validates DNS answers, direct cross-worker HTTP both ways, and ClusterIP/service-name access from both workers. Default/check mode contacts no cluster. A reviewed cluster UID and fresh namespace are required; cleanup checks ownership and namespace UID even on probe failure. Private result summaries and diagnostics stay ignored. These probes do not validate ingress, network-policy isolation, storage, reboots or backup/restore.

The separately invoked etcd backup check creates one named local snapshot, copies it and the unchanged matching server token into fresh protected workstation storage, compares source/copy SHA256 and size, verifies the snapshot integrity trailer, and confirms node readiness. Default/check mode connects nowhere. It does not restart RKE2, prune snapshots, use cloud storage or restore the datastore. Transfer and byte-integrity checks do not prove database consistency or restore success. Keep the snapshot/token together outside Git; a credential ZIP is not a datastore backup. The human command is documented in infrastructure/ansible/RKE2.md.

Sequential reboot verification is a separate explicit live action for the bootstrap-only cluster. It checks a verified off-node backup, then reboots the two workers before the single server, stopping on any failure. Each node must return over SSH with a new boot ID, start its enabled RKE2 service automatically, retain enforcing SELinux and host network prerequisites, and report the new boot ID plus Ready in the API. The API/datastore and all selected nodes must be ready before moving on. The server reboot causes temporary API downtime. A separate disposable workload smoke run verifies DNS/cross-worker traffic afterward; this is not application draining, HA failover, storage persistence or restore validation.

Application volume data is separate from etcd recovery. The authored Keycloak database uses a 4Gi retained node-local PV; node/path still require explicit selection and host directory/SELinux preparation. Its directory shares the OS filesystem, and the PVC capacity is not an enforced quota. Local volume availability depends on its worker/disk. Replicated storage is a separate decision with host, network, capacity and compatibility prerequisites; neither replication nor Retain replaces application-data backups.

The growth design covers Harbor image retention, portal PostgreSQL, Nextcloud personal files/photos and OpenBao. Proposed Longhorn storage keeps two replicas on distinct workers, leaves control-1 out of application-data storage, starts with an approximate 80–100Gi logical budget and conserves OS/snapshot headroom. Add dedicated worker disks as actual usage grows. The existing static Keycloak specimen is not yet replaced. Big Bang has no built-in Longhorn add-on in the pinned release; its custom-package contract can declare a pinned upstream chart for Flux reconciliation before stateful apps. Host prerequisites, version compatibility, actual claims and independent backups require review before installation.

Longhorn and Rancher inputs are prepared but unselected and individually suspended; the outer release/seed stay paused. Rollout order is host/RKE2 preparation, Flux/Big Bang foundations, Longhorn readiness plus a disposable PVC persistence check, then stateful applications. Keycloak waits for Longhorn; its alternate dynamic-claim prerequisite removes static node/path binding. Rancher Helm needs reviewed DNS/TLS and a required external bootstrap-values Secret, not a Longhorn volume. Its OIDC API configuration waits for Keycloak. Next pre-bootstrap test is read-only Longhorn host compatibility; it does not install host packages or Longhorn. Replica persistence/failover testing waits for later activation.

Storage and management rollout ownership

Infrastructure Ansible owns RHEL/RKE2 creation and recovery, and separately approved storage host prerequisites. Big Bang custom packages declare the pinned Longhorn/Rancher charts; Flux reconciles them. Both packages remain unselected and suspended, as does the outer Big Bang release. Preparation and offline rendering perform no bootstrap or host changes.

After reviewed host compatibility and prerequisites, bring up Flux/Big Bang foundations, Longhorn and a disposable PVC write/recreate/reattach test, then stateful apps. Keycloak's PVC/Helm dependency waits for Longhorn. Rancher Helm needs DNS/TLS and required external bootstrap values; it stores management state in the Kubernetes datastore and has no fabricated Longhorn dependency. Gated Ansible OIDC/admin API configuration follows ready Keycloak. The legacy direct Rancher Helm installer refuses by default under Big Bang ownership.

Storage uses two replicas on distinct workers, excludes control-1 from data replicas, preserves root-disk headroom and retains released volumes. The initial logical budget is approximate and not a quota. Nextcloud personal data, databases and secrets require independent protected backups and restore tests. The next pre-bootstrap test is read-only host compatibility; real PVC persistence/failover tests wait for later approved Longhorn activation.

Physical RHEL architecture and repeat procedure

Read context first, then workstation/node/platform detail, followed by the ordered operations and focused protocol, installation, access and lifecycle views. This is the interactive physical procedure. Session status, approvals and execution results remain in the repository handoff and execution journal.

  1. Prepare reviewed PXE configuration — Review target, network, media and fresh private configuration.
  2. Review target, disk and action scope — Confirm selected node, disk, data loss and access scope.
  3. Activate PXE and select network boot — Start reviewed services and reach the indefinite GRUB menu.
  4. Install RHEL with reviewed settings — Review layout and accounts before committing the installation.
  5. Restore disk-first and boot installed OS — Restore firmware order and verify the installed disk boots.
  6. Verify identity, key login and sudo — Establish trusted access and verify fresh login and sudo.
  7. Stop owned services and retain evidence — Verify scoped shutdown and preserve original services and evidence.

Responsibilities and scope

The operator chooses the target, handles firmware and Anaconda, approves action scope and compares trusted host identity. Ansible owns workstation service configuration/lifecycle; the router owns DHCP leases. Standard SSH tools provide the installed-host access handoff. Viewing documentation runs no provisioning commands.

This procedure describes the proven PXE transport and interactive install path. Disk/credential automation is not a deployable replacement. Each run still needs its own target/action approval and completion evidence.

1. Prepare reviewed PXE configuration

Use a physical target on the reviewed wired IPv4 LAN. The router remains the DHCP allocator. Required workstation tools and existing service identities must already be available: Ansible, dnsmasq, nginx, nftables, systemd, GRUB validation and media tools. Installing packages or staging media is a separate reviewed action; do not repeat either against existing media merely to start a session.

Verify the RHEL10.2 x86_64 DVD checksum against its trusted source. Preserve its complete tree including .treeinfo, plus matching vendor EFI loaders, kernel and initrd in the dedicated HTTP/TFTP roots. Media must be root-owned, read-only and free of symlinks/special files. Use the previously accepted Secure Boot path and exact GRUB lookup path; do not substitute an untested protocol.

Private inputs identify the interface, workstation/client address, client MAC, subnet, separate existing service users/groups, media paths and fresh review directory. No passwords, hashes or private keys belong there. Input schema · Offline transport preparation · Media-staging implementation.

ansible-playbook -i localhost, -c local pxe/pilot/prepare.yml -e @<private-target-inputs.yml>

This writes inert mode0600 review files into a new mode0700 directory, not live services. Review dnsmasq/nginx/GRUB/ingress output and record exact source hashes, original menu hash and interface identity in the private activation snapshot. Never reuse an old target's private snapshot implicitly.

Operator
Select the physical target and review media, network and generated configuration.
Automation
Ansible renders private configuration only; preparation does not stage or activate.
Evidence / stop
Verified source/assets, reviewed hashes and a fresh output directory; stop on missing prerequisites or unexpected state.

2. Review target, disk and action scope

Review exposure and lifetime before service activation; review network boot and installer inspection separately from disk erasure. For the interactive single-drive path, inspect the sole internal drive's model, capacity and device name. Multiple drives, ambiguous identity or unexpected capacity require resolution before proceeding. A name such as nvme0n1 alone is not a persistent identity and must not replace automated disk guards.

Approve the selected node's existing-data loss, intended layout and account privileges explicitly. Approval for a previous node does not transfer. Preserve other installed nodes and unrelated workstation services. Enter account passwords locally; do not collect them in chat, command arguments or logs.

Operator
Approve the concrete target, service exposure/lifetime, disk erasure and account scope at their respective boundaries.
Automation
Service preflight checks configuration and ownership; it does not discover or attest the physical disk.
Evidence / stop
Sufficient selected-disk evidence and explicit node-specific approval; stop for ambiguity or scope changes.

3. Activate PXE and select network boot

Run the reviewed target-specific activation launcher with private automatic logs. activate.yml consumes a reviewed snapshot containing the private review directory, four config hashes, original-menu hash, interface and server address. It requires explicit activation approval; retry-menu selection is a separate exact-hash choice, not a way to bypass retained-state checks. See lifecycle preflight and recovery.

The default lifetime is30minutes. For a long installation, explicitly approve manual shutdown and use lifetime0, which maps to RuntimeMaxSec=infinity; verify the reported runtime property. Do not start an installation that a service timeout could interrupt.

Keep Secure Boot enabled. Select wired UEFI IPv4 PXE through the one-time boot menu when reliable. Otherwise record the existing order and use Startup → Primary Boot Sequence to temporarily put network ahead of disk. Plan to restore disk-first before normal disk boot. Inspect firmware options rather than changing unrelated settings or disabling Secure Boot.

The client requests an address from the router and boot metadata from proxy dnsmasq, then obtains vendor shim/GRUB and configuration via TFTP. The reviewed GRUB menu uses default=0 and timeout=-1; default exits without starting installation. The separate interactive-installer entry must be selected deliberately after approval. Exit alone does not guarantee a disk boot. GRUB has no Linux disk-inventory service or remote shell. Kernel/initrd then use HTTP for installer runtime and packages.

Proxy/TFTP template · Menu template · HTTP template. Secure Boot does not authenticate GRUB configuration or Kickstart; MAC/IP filtering is not authentication. UEFI HTTP boot is not this procedure's proven route.

Operator
Run approved activation, then select wired UEFI IPv4 PXE; record any temporary boot-order change.
Automation
Dedicated services answer client-driven DHCP/proxy/TFTP/HTTP exchanges.
Evidence / stop
Reviewed indefinite GRUB menu reached; stop on wrong target, trust error, missing service or unexpected boot behavior.

4. Install RHEL with reviewed settings

Select the interactive RHEL10.2 installer only within the approved scope. Choose language and continue to Installation Summary. Inspect Installation Destination before changing storage; select only the reviewed system disk.

Choose Custom. After node-specific erase approval, remove old Windows/EFI/BitLocker/recovery partitions on that disk. Add this reviewed local-lab layout:

MountCapacityDevice typeFilesystem
/boot/efi600MiBStandard PartitionEFI System Partition
/boot2GiBStandard PartitionXFS
/Remaining spaceOrdinary LVMXFS

No separate home/swap, encryption or FIPS in this reviewed local-lab profile. These are explicit choices, not a production/compliance baseline. Check the actual capacities/types rather than assuming automatic partitioning matches. A disabled Update Settings button can mean there are no unapplied edits. Click Done and inspect Summary of Changes: only the selected disk may change. Accept the reviewed proposal.

Choose Minimal Install, the selected node's hostname and wired networking. Keep root disabled. Create the approved named user with Make this user administrator and password required; enter the password locally. Review timezone/time settings. Confirm there are no unresolved installer warnings, then Begin Installation commits the disk changes.

Keep the workstation and source network available throughout package installation. Wait for the explicit completion result and pause before reboot. GUI partition edits and a running progress indicator are not completion evidence.

Operator
Inspect disk, approve data loss, configure the custom layout and named administrator, then review and begin.
Automation
Anaconda applies the reviewed layout and installs packages from the HTTP DVD tree.
Evidence / stop
Explicit successful installation completion; stop on unexpected disks, storage proposals or errors and retain source availability.

5. Restore disk-first and boot installed OS

After installation completes, restore disk-first Primary Boot Sequence if network-first was used. Firmware entry may require the normal post-install restart; ensure the next normal boot selects the installed disk rather than repeating the network installer. Retain Secure Boot. Do not interpret a GRUB exit as restoration of the saved boot order.

If PXE still starts after saving disk-first Primary Boot Sequence, do not select the installer again. Inspect actual UEFI boot entries and other firmware boot sequences before concluding the saved order is effective. After installation has completed, a temporary Ethernet disconnect during reboot can allow local disk boot; reconnect after reaching the installed OS. This workaround does not establish correct connected-reboot behavior: verify that separately rather than marking firmware ordering fixed.

Verify that the installed RHEL login appears, log in as the named user and confirm the expected hostname. Record actual resulting storage and network state during verification. Keep source services until the installer no longer needs them; shutdown is explicit, not implied by reboot.

Operator
Restore original/disk-first boot order after completion and observe the installed OS boot.
Automation
Firmware boots the installed local disk; no automatic withdrawal/reboot controller is provided by this procedure.
Evidence / stop
Installed OS login and correct hostname without an installer loop; preserve recovery access if boot fails.

6. Verify identity, key login and sudo

Use the access handoff detail: physical identity/fingerprint comparison, approved public-key enrollment, fresh key login before hardening and a new login after it. Verify password-authenticated sudo as the named user. Check actual storage, hostname, network and time; record failures as unresolved instead of declaring readiness from installer completion.

OS/access completion does not authorize RKE2 or prove host readiness. Review repositories/Python, time, SELinux, NetworkManager/CNI, firewall, kernel prerequisites and capacity under the separate platform boundary.

Operator
Compare trusted identity, enter credentials locally and retain an existing recovery session until fresh access succeeds.
Automation
Standard SSH tools and reviewed policy validation support enrollment/hardening; no automatic bootstrap-account lifecycle is assumed.
Evidence / stop
Fresh key-only login and password-authenticated sudo, plus reviewed OS state; stop on identity/access mismatch.

7. Stop owned services and retain evidence

After source is no longer needed, use the separately approved shutdown entrypoint and identity-checked tasks. Stop only the recorded dedicated units/processes; verify listeners are gone before removing the matching dedicated guard. Compare original system/libvirt/default nginx state. Never broad-kill processes, reset all failed services or flush unrelated firewall tables.

Retain runtime/log records, reviewed media, backups and failed-run evidence. Emit a compact sanitized completion result separate from private operational logs. A mismatch means shutdown is incomplete and requires inspection. Fresh activation must not overwrite those retained paths; apply the recovery contract before reuse.

Operator
Authorize shutdown when source is no longer needed and review the result.
Automation
Ansible verifies exact ownership, stops only recorded resources and checks original services.
Evidence / stop
Owned units/processes/listeners/guard absent, original services preserved and evidence retained; otherwise report incomplete.

Service lifecycle, evidence and recovery

Fresh activation requires absent dedicated unit/runtime/log/table state, available reviewed ports, correct wired interface/address and masked/inactive default nginx. Original system/libvirt dnsmasq identities are recorded privately. Existing roots, failed units or listeners are reasons to stop and inspect, not cleanup targets.

Review source hashes, root ownership/read-only media, one GRUB menu and matching EFI/kernel/initrd assets. Copy configuration into a unique root-controlled session, rehash before use, record the transaction and apply the exclusive dedicated nft table before nginx validation or service startup can bind on the LAN. The HTTP service uses a separate identity. Launch only dedicated transient units; capture invocation ID, PID, execution path and actual runtime property. Verify required listeners and original services.

Default1800seconds remains bounded; approved manual-stop sessions map0 to explicit infinity. A timer must not cut off an active installation. Failed activation uses bounded identity-checked rollback. A reset/retry requires inspection of the protected transaction, current unit invocation identities/PIDs, listener and guard state. Clear only exact matching stopped failed units; verify unloaded/stopped, then preserve retained roots under fresh non-overwriting held names before a new activation. Recovery code specific to a prior transaction is not a general retry entrypoint.

Use private automatic operational logs and bounded exit summaries, mode0600, with Ansible no_log and no terminal/password recording. Enter sudo only at the local prompt. Retain earlier held roots and private inputs. Do not publish raw operational logs or copy credentials into tracked documentation.

Placement and transaction recording · Copy integrity · Identity verification · Ingress guard.

Installed-host trust and access handoff

At physical console, verify hostname/address and compare the complete SSH host fingerprint with the workstation's connection prompt before accepting trust. A network scan alone is not independent identity proof. Keep private keys and encrypted backups in protected custody; enroll the existing public key with standard SSH tooling over a host-verified connection.

Inspect installed-host SSH availability first. If key enrollment needs temporary password SSH, review and approve that bounded access window explicitly; do not assume it is enabled or silently change installer/host security. Keep root SSH disabled and preserve console/current access. Before hardening, prove a fresh public-key-only login.

The final policy requires publickey authentication, disables password and keyboard-interactive SSH and root SSH, and retains PAM for password-authenticated sudo. Validate SSH syntax and effective policy for the actual user/client and root before reload. The retained tested policy helper refuses an existing managed drop-in and requires a preverified key login; inspect before reuse. Its source remains in the historical console directory; the failed HTTP enrollment path is not part of this procedure.

After reload, prove a separate fresh key-only login and password-authenticated sudo; only then close recovery access. Type passwords/passphrases locally, never in chat, logs, HTTP/TFTP or command arguments.

Host readiness and platform ownership

After OS/access, separately assess repositories/Python, time, kernel prerequisites including the RHEL10 nf_conntrack dependency, networking/CNI, firewall, SELinux and capacity. Infrastructure Ansible owns host/RKE2/Rancher configuration. Rancher manages platform-admin cluster lifecycle; Flux reconciles GitOps, with Big Bang supplying curated platform packages. Tenant enrollment Git owns tenant foundations and registration; application repositories own application configuration. Historical Fleet and VM/AWS lab workflows are not active deployment paths. None of these later changes follows automatically from installation approval.

Repeatability limits

The procedure requires existing reviewed media/tooling and operator firmware, installer and host-trust steps. There is no generic one-command physical installer or remote disk-inventory agent. The separate offline Kickstart candidate deliberately aborts and its persistent-disk guards must not be weakened to reuse interactive disk evidence. Fixture-tested bootstrap components do not prove native unattended disk/PAM/access behavior. These capability boundaries are requirements for safe repetition, not additional operating paths.

Keep session results and troubleshooting history in HANDOFF.md and infrastructure/EXECUTION-JOURNAL.md. Do not mark a new node installed, access-verified or ready from another node's result.
